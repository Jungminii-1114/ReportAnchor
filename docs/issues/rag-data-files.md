## RAG 데이터 준비 완료 및 주요 파일 역할 공유

현재 추출 데모를 기준으로 **① 입력 로더·검증, ② 청킹**을 구현했습니다. 다음 단계는 생성한 청크를 사용하는 검색 인덱스 구축입니다.

### 주요 데이터 4개

| 파일 | 단위 | 목적·용도 |
|---|---|---|
| `manifest.json` | 문서당 객체 1개 | 문서 ID, 원본 해시, 출처 URL, 페이지 수, 파서 버전 관리. 문서·버전 식별에 사용 |
| `pages.jsonl` | 페이지당 한 줄 | 페이지 전체 텍스트와 추출 상태 보관. 페이지 단위 확인과 주변 문맥 확장에 사용 |
| `blocks.jsonl` | 추출 블록당 한 줄 | 텍스트와 블록 ID·페이지·좌표 보관. **청킹의 직접 입력**이자 원문 추적 기준 |
| `chunks.jsonl` | 검색 청크당 한 줄 | 인접 블록을 묶은 검색용 데이터. **BM25·임베딩 검색의 직접 입력**으로 사용 |

```text
manifest + pages + blocks → 입력 검증 → 청킹 → chunks → 검색 인덱스
```

추출 블록은 PDF의 출력 단위이고, 청크는 RAG에서 검색할 단위입니다. 네 파일을 모두 LLM에 넣는 구조가 아닙니다.

### 이번 구현

- [x] 문서·버전·페이지 참조와 중복 ID 검증
- [x] 같은 페이지의 인접 블록을 최대 1,000문자로 청킹
- [x] 최대 120문자 범위의 완전한 후미 블록 중첩. 실제 중첩은 0일 수 있음
- [x] `chunk_id`, 원문 블록 ID, 문자 구간, 페이지·좌표 보존
- [x] 원문 `text`와 정규화한 `search_text` 분리
- [x] 입력 파일 보존 및 동일 조건의 청크 ID 재현 확인

### 실행 결과

**117쪽 · 3,105블록 → 180청크**를 생성했습니다. 블록 원문 전체의 문자 구간 보존과 청크 복원을 검증했고, 새 데이터 준비 테스트 10개 및 기존 추출 테스트 9개가 통과했습니다.

입력은 기존 `data/processed/pymupdf_demo/.../`의 세 파일이며, 출력은 다음 위치입니다.

```text
data/processed/rag/kistep_2025_plan_0530d100e085/3382f591c928/chunks.jsonl
```

### 공유 사항

- 청킹 설정은 초기 기준입니다. 검색 평가 후 길이·중첩·경계 규칙을 조정합니다.
- 페이지·일부 제목 경계를 활용하지만, 의미상 절 구분이나 표 구조의 정확성을 보증하지 않습니다.
- 현재 청크의 검증 상태는 `unverified`입니다. 청크 생성 성공은 사실 검증 완료가 아닙니다.
- 최종 Parser/VLM 출력 계약은 해당 담당자와 합의합니다. 이번 구현에서는 모델 호출이나 PDF 재파싱을 하지 않았습니다.
- 보조 파일 `chunking_report.json`에는 설정·입력 해시·생성 통계를 저장합니다.
