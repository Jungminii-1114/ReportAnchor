# Query Agent — MVP 3단계 실행 구조

> 상태: **MVP 최상위 Small → Big → Small 구조 확정(2026-10-31), T-01·T-02 및 N-01~N-06·N-10·N-11 개념 계약 확정(2026-11-28)**. Big Node 5종 중 T-01~T-03을 MVP 우선 대상으로 두고, Small Node N-01~N-11을 등록한다. T-03(N-07~N-09) 상세 설계·실행 예산·통합 구현·평가 결과는 미완료다.
>
> 목적: **N-10 `route_query`(Small Node) → 선택된 T-01/T-02/T-03(Big Node) → N-11 `deliver_result`(Small Node)** 순서로 요청을 처리한다. Big Node 내부는 업무별 Small Node의 사전 정의된 고정 워크플로로 실행한다.
>
> 결정 근거: [하네스 아이디어 백로그](idea-backlog.md#0-결정-현황-2026-10-30). DSH의 실행·이벤트·도구 계약을 참고하되, MVP는 DSH식 자율적인 도구 반복 호출을 기본 실행 방식으로 사용하지 않는다.
>
> **명칭 통일:** [Big Node(T-xx) / Small Node(N-xx) 이름 기준](naming-conventions.md). 기존 문서의 '작업 Tool'은 Big Node, '최소 단위 노드'는 Small Node와 같은 뜻이다.
>
> **Small Node 설계 LIST:** [최상위 공통 N-10·N-11 및 Big Node 내부 N-01~N-09, 총 11종](query-agent-node-list.md). [Big Node 폴더](big-nodes/README.md)는 업무별 워크플로를, 이 문서는 최상위 실행 구조를, 별도 LIST는 전체 Small Node의 식별자·책임을 관리한다.

## 1. 전체 실행 흐름

```mermaid
flowchart TD
    U["사용자 질문 + 대상 문서/검토 기준"] --> S10["① Small Node · N-10 route_query<br/>요청·문서 범위·권한 확인 및 라우팅"]
    S10 --> D{"MVP 지원 요청이며 실행 가능한가?"}
    D -->|"아니요"| S11["③ Small Node · N-11 deliver_result<br/>검증 결과·출처 또는 종료 사유 제공"]
    D -->|"예"| R{"② Big Node 하나 선택"}
    R -->|"T-01"| B1["Document QA<br/>내부 Small Node 4종"]
    R -->|"T-02"| B2["Criteria Review<br/>내부 Small Node 5종"]
    R -->|"T-03"| B3["Comparative Analysis<br/>내부 Small Node 6종"]
    B1 --> S11
    B2 --> S11
    B3 --> S11
```

**고정 워크플로의 의미:** 전체 단계와 허용 분기·도구 호출 경계는 설계 시 결정한다. 입력에 따라 미리 정의한 조건부 분기, 건너뛰기, 제한된 재시도는 허용하지만, Agent가 실행 도중 도구의 호출 순서나 실행 그래프를 임의로 확장하지 않는다.

**메인 에이전트와 tool (2026-11-05 결정):** N-10과 N-11은 사실상 **메인 에이전트의 역할**이고, 각 Big Node는 **메인 에이전트가 호출하는 tool**이다.

- **N-10:** 요청을 확인하고 호출할 tool을 고르거나 실행 전에 종료한다.
- **Big Node:** 내부 Small Node를 고정 워크플로로 실행하고 `WorkflowResult`를 메인 에이전트에게 돌려준다. 메인 에이전트는 내부 Small Node를 직접 호출하지 않는다.
- **N-11:** tool 결과를 받아 사용자에게 전달할 답변을 작성한다. tool 결과에 없는 내용을 사실로 추가하지 않는다.
- **호출 제한:** 요청당 Big Node 1개만 호출하며, 결과를 본 뒤 다시 호출하지 않는다. 검증 후 보정은 Big Node 내부에서 끝낸다.
- **tool 인자:** LLM은 호출할 tool만 고르고 인자는 하네스가 원본 요청에서 채운다. `question`은 MVP에서 사용자 쿼리 원문 그대로다.
- **N-11 문장 재확인 (2026-11-28):** MVP에서는 별도 사후 재확인 장치를 두지 않고 프롬프트 지침만 적용한다. 상태·판정·출처는 Python이 `WorkflowResult`에서 직접 조립하며, AI 요약 vs 정형 템플릿 비교 실험은 [백로그 4.10](idea-backlog.md#410-n-11-후속-평가--마지막-단계-요약-왜곡synthesis-drift-측정-및-ai-요약-vs-템플릿-비교-실험-2026-11-28)에서 관리한다.

**MVP 고정 실행 단위:** **N-10 → Big Node 1개 → N-11** 순서를 확정한다. T-04·T-05는 계획만 유지하며 MVP 라우팅 대상에서 제외한다. 입력 불충분·권한·지원 범위 문제로 Big Node 실행이 불가능하면 **N-10 → N-11**로 종료 사유를 전달한다. Big Node 연쇄 호출·자율 재계획·다중 Agent는 기본 경로에서 제외한다.

## 2. 세 단계의 책임과 입출력

| 단계 | 책임 | 입력 | 출력 및 저장 |
|---|---|---|---|
| **① Small Node N-10 `route_query`** | 원본 질문·문서 ID/버전·허용 범위·권한·필수 조건 검증 후 **T-01/T-02/T-03 중 하나로 라우팅**. 불충분·미지원이면 실행 전 종료 | 원본 요청(`ReviewRequest`: 질문, 선택 문서와 버전·범위, 명시적 조건) | 실행 가능 시 `NodeResult[RoutedTask]`; 불가 시 `outcome`=`needs_clarification`/`unsupported_request`, 권한·버전 위반은 `error` ([N-10](small-nodes/N-10.md)) |
| **② Big Node T-01/T-02/T-03** | 업무별 **고정 Small Node 워크플로**로 검색·검토·비교 및 검증 수행. 분기·재시도는 사전 정의 | 유효한 `RoutedTask`, 문서·색인/아티팩트 참조, Big Node별 설정 | `WorkflowResult`, 근거/아티팩트 참조, 실행 진단 (체크포인트는 미정) |
| **③ Small Node N-11 `deliver_result`** | Big Node의 검증 결과(`WorkflowResult.outcome` 최우선 매핑 포함) 또는 N-10의 실행 전 종료 사유를 **추가 판단 없이** 전달 | `WorkflowResult` 또는 라우팅 종료 상태·사유 | 사용자 결과(`FinalReview`, `result.kind` 분기), 근거 출처·검증 상태·미확인 항목·오류 |

**주의:** N-10은 기준별 판정·근거 검색을 수행하지 않으며, N-11은 새로운 결론이나 미검증 근거를 생성하지 않는다. 입력이 명확하고 유효하면 사용자에게 재확인을 요구하지 않고 곧바로 Big Node를 실행한다.

## 3. Big Node·Small Node와 내부 기능의 경계

- **Big Node(목적별 고정 워크플로, T-xx):** 사용자 목적 하나를 해결하는 하위 실행 그래프. **T-01/T-02/T-03 세 개만 MVP 라우팅 대상으로 확정**하고, T-04/T-05는 계획만 유지한다. Big Node를 자율적으로 연쇄 호출하지 않는다.
- **Small Node(N-xx):** Big Node 내부 공통·전용 단위 **N-01~N-09**, 상위 입구·출구 단위 **N-10·N-11**. 세부 검색(Dense/BM25/RRF/Reranker), 원문 문맥 보조, 결정적 계산은 필요한 Small Node의 **내부 기능**이다.
- **하네스 공통 책임:** 요청·결과 계약 검증, Tool 등록·권한, **H-02 아티팩트 캡처(MVP 구현 대상)**, 실행 진단·취소·오류·시간/토큰 예산. H-03 체크포인트/재개는 미정. [저장 설계](artifact-capture.md)
- **모델 실행 경계 (미반영 · 백로그):** 제품 목표는 외부 전송 0건이고 개발 클라우드는 공개 자료에 한정하지만([모델 운용 방침](idea-backlog.md#01-모델-운용-방침-2026-11-24)), 문서 열람 권한 검사만으로는 질문 원문·문서 제목·근거가 클라우드로 전송되는 것을 막지 못한다. N-10·N-11을 포함한 모든 모델 호출 전 단일 어댑터에서 정책을 강제하는 방안은 [백로그 4.11](idea-backlog.md#411-하네스-모델-실행-경계--로컬-전용-강제-및-개발-클라우드-공개-자료-검증-정책-2026-11-28)에서 관리하며, 이 문서의 MVP 계약에는 아직 포함하지 않았다.
- **LLM 역할:** 라우팅이나 워크플로 내부의 제한된 해석·요약 등에 사용 가능하다. **LLM 사용 자체는 자유로운 도구 호출 권한을 의미하지 않는다.** 모델·기술 선택은 미확정.
- **검증 경계:** 근거 관련성, 원문 데이터 정확성, 최종 주장·인용 정합성을 구분한다. 검색 순위나 Reranker 점수가 사실 검증의 대체물이 되지는 않는다.

### Big Node 워크플로별 작성할 항목

각 목적별 Tool은 다음 요소를 별도의 설계 단위로 기록하고 결정한다.

| 항목 | 정의할 내용 |
|---|---|
| 목적 / 지원 질문 | 해결하는 사용자 문제와 지원하지 않는 범위 |
| 입력 계약 | `RoutedTask` 내 필수 조건, 허용 문서 및 참조 버전 |
| 고정 실행 단계 | 처리 노드의 순서·의존성·조건부 분기·필요 도구 |
| 근거·검증 | 원문 위치 조회, 표/각주/단위 검증 책임 및 판단 보류 조건 |
| 예외와 실행 예산 | 오류 분류, 제한된 재시도, 타임아웃, 토큰/도구 호출 제한 |
| 결과 계약 | `WorkflowResult`의 업무별 내용과 공통 상태값 |
| 비교 실험 | 품질·근거 정합성·지연·비용 지표와 후속 방식 교체 기준 |


## 4. 목적별 Big Node 계획 — 5종

**Small Node 목록 연계:** [전체 11종 Small Node LIST](query-agent-node-list.md)에서 T-01~T-03 내부의 N-01~N-09 조합과, 모든 요청의 공통 입구 N-10·출구 N-11을 확인한다. 이 문서는 Big Node의 업무별 워크플로 단계·분기에 집중한다.

다음 Tool은 **메인 에이전트가 호출하며 사용자 요청을 처리하는 작업 단위**다. `retrieve_evidence`, `get_source_context`, `calculate`처럼 워크플로 내부에서 재사용하는 기초 기능과 구별한다.

| ID / Big Node (설계명) | 요청 예시 | 핵심 목표 | 계획 상태 |
|---|---|---|---|
| T-01 **Document QA** | "이 보고서에 제시된 핵심 성과가 뭐야?" | 특정 질문에 맞는 답변과 직접적인 원문 근거 반환 | **MVP 우선 / 개념 계약 확정** |
| T-02 **Criteria Review** | "이 계획서가 명시한 평가 조건을 충족했는지 확인해 줘." | 사용자 지정 기준별 충족·미충족·확인 불가 판정 | **MVP 우선 / 개념 계약 확정** |
| T-03 **Comparative Analysis** | "2024년과 2025년 실적을 비교해 줘." | 동일한 비교 기준에서 문서·기간·값의 차이를 분석 | **MVP 우선 / 1차 설계** |
| T-04 **Claim Verification** | "이 보고서의 비용 절감 주장을 근거로 검증해 줘." | 주장별 근거·반증 검토와 검증 가능 범위 표시 | 계획 유지 / 상세 설계 보류 |
| T-05 **Document Summary** | "보고서 전체를 핵심 중심으로 요약해 줘." | 문서 전체를 구조적으로 다루는 출처 기반 요약 | 계획 유지 / 상세 설계 보류 |

**범위 결정:** T-01, T-02, T-03을 **구현 준비를 위한 1차 설계 우선 대상**으로 한다. T-04, T-05는 계획에서 삭제하지 않고, 현재 단계에서는 독립 Tool 구현을 확정하지 않는다. 모든 항목은 문서·기관·평가셋에 종속되지 않는 범용 경계로 정의한다.

### 4.1 세 Tool에 공통으로 적용할 원칙

- **사전 정의된 순서:** 요청 확인(1단계)은 선택된 Tool에 검증된 `RoutedTask`를 넘긴다. Tool 내부의 실행 노드와 분기는 미리 정의한다. LLM에 무제한 도구 호출이나 실행 계획 생성 권한을 부여하지 않는다.
- **근거 확보:** 질문 또는 사용자가 명시한 검토 기준과 허용된 문서 범위로 `retrieve_evidence`(N-01)를 호출한다. 검색은 [문서 처리 파이프라인](document-pipeline.md)의 Dense + BM25 + RRF 후 **Reranker를 적용하는 구성으로 구현 확정(2026-11-24)**했으며, Reranker 모델 선정과 활성 조건은 비교 실험으로 결정한다. 초기 검색 실패 자체를 반증으로 해석하지 않는다.
- **원문 대조:** 검색 후보는 `get_source_context`(N-02)를 통해 원문 문맥과 출처 위치를 확인한다. **확장 문맥에 포함된 인접 블록·페이지 참조(`expanded_source_refs[]`)도 함께 보존**해 검증 통과 주장이 실제 근거 위치와 어긋나지 않게 하며, T-02 검증에서는 N-03에 `original_criterion`을 함께 넘겨 **사용자 기준 원문(`original_text`)과의 연산자·임계값·범위 일치 여부**까지 대조한다. 후보 순위와 원문 추출의 검증 상태, 최종 결론의 신뢰 상태를 구별한다.
- **제한된 재시도:** **T-01과 T-02 모두 MVP에서 재검색은 0회로 확정**한다(일시적 실행 실패의 재시도는 하네스 실행 정책 H-08에서 별도 관리). T-01은 자료와 충돌하는 주장만 내부에서 1회 보정하고, T-02는 MVP에서 보정 호출을 하지 않고 검증 탈락 조건을 `unverifiable`로 하향한다. T-03의 재시도, 그리고 세 Big Node 공통의 후보 수(Top-k)·시간·토큰 예산은 추후 확정한다(T-02의 소배치 검증·예산 소진 시 부분 완료 반환은 [백로그 4.12](idea-backlog.md#412-t-02-후속-개선--기준별소배치-검증-파이프라인-및-예산-소진-시-부분-완료-반환-2026-11-28)). 원본 쿼리 증폭(PRF/Multi-query/HyDE)은 도입하지 않는다.
- **일관된 출력:** 업무별 내용은 달라도 `WorkflowResult`를 통해 `status`, `outcome`, `evidence_incomplete`, 근거 참조, 검증 결과, 미확인 항목, 오류, 실행 아티팩트 참조를 반환한다. 3단계의 N-11은 항목 개수보다 **`WorkflowResult.outcome`을 최우선으로 매핑**해 사용자에게 전달한다(예: T-02의 `unsupported_structure`·`needs_clarification`은 `criteria_review` 안에서 미처리 사유와 함께 그대로 표시, [N-11 매핑 표](small-nodes/N-11.md#32-워크플로-결과--사용자-상태-결정적-매핑-2026-11-28)).
- **근거 없는 생성 금지:** 근거 부족을 그럴듯한 답변으로 보완하지 않는다. `WorkflowResult`는 공통 계약처럼 실행 상태 `status`와 업무 결과 `outcome`을 나눈다. T-01의 값은 [T-01 결과 상태](big-nodes/T-01.md#결과-상태-2026-11-05-결정), T-02의 값은 [T-02 결과 상태](big-nodes/T-02.md#5-결과-계약과-상태-3축-2026-11-28-확정)에서 확정했으며, T-03의 `outcome`과 실제 Python 스키마는 미확정이다. 실행 전 명확화·미지원은 N-10이, 기준 구조화 후 명확화·미지원 구조는 T-02가 각각 `outcome`으로 구분해 N-11에 넘긴다.

## 5. 기존 설계·구현 기준선과의 관계

- **기존 구현 브랜치(`origin/JM`) 통합 기준선 (2026-11-28 명시):** `origin/JM` 브랜치에 이미 `DocumentQAWorkflow`(T-01), `CriteriaReviewWorkflow`(T-02), `BM25Retriever`, 공유 Ollama 클라이언트(`rag/llm/ollama_client.py`) 및 `N-01`~`N-06` 구현이 존재한다. 본 문서는 이를 처음부터 중복 구현하지 않고 **통합 재사용 후보 기준선**으로 삼되, T-01/T-02별 상이한 결과 타입은 하네스 경계 어댑터로 공통 `WorkflowResult`·`FinalReview` 계약에 맞춘다. 남은 구현 범위는 **Dense 검색(`rag/retrieval/dense.py`) · RRF · Reranker · N-10 · N-11 · H-02 아티팩트 캡처 · T-03(N-07~N-09)**과 계약 불일치 정합이다.
- [문서 처리·검색 파이프라인](document-pipeline.md)은 **작업 Tool 내부의 검색 능력** 또는 사전 문서 등록 단계로 유지한다. **Reranker는 구현 확정(2026-11-24)**이며 후보 모델 선정·활성 조건은 비교 실험 후 결정한다.
- **쿼리 증폭·재작성은 H-12 백로그**에 유지하고 MVP 기본 라우팅 및 검색 경로에 포함하지 않는다. 도입하면 Big Node 내부가 아니라 밖의 별도 노드로 붙인다.
- [DSH 분석 참고](../references/deepseek-harness/README.md)는 Agent 실행 이벤트, Tool 호출 전후 정책, Session 기록의 참고 자료다. 자유 실행 루프를 그대로 도입하지 않는다.
- **MVP 이후 변경 가능:** 더 높은 자율성이 실제 평가에서 이점을 보일 경우 Tool 조합, 재계획, 제한적 Agent Loop를 별도 실행 전략으로 실험한다. 현재 결정된 3단계 계약을 기본 비교 대상으로 보존한다.

## 6. 아직 결정하지 않은 것

**Small → Big → Small 최상위 구조, T-01·T-02 워크플로 및 N-01~N-06·N-10·N-11의 개념 계약을 확정했다.** T-03(N-07~N-09)은 1차 설계 상태이고 T-04/T-05는 후속 후보다. 아직 미정인 것은 T-03 상세 계약, 실제 Python/OpenAPI 스키마, `origin/JM` 구현과의 계약 정합 및 어댑터 구현, 검색·실행 예산, **H-02 아티팩트 저장의 실제 구현·보존 정책과 체크포인트 도입 여부**, 평가셋·지표 통과 기준이다. 이 문서는 **설계 정본**이며 통합 코드 작성·성능 검증 완료를 뜻하지 않는다.
