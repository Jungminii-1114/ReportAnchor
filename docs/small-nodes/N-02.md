# N-02 · get_source_context — 원문 근거 조회

> **상태:** **MVP 문맥 확장 방식 확정(2026-11-02): 고정 길이 확장.** 문서 구조 기반 확장은 추후 개선 후보. 그 외 상세 입력·출력 필드, 예외 정책, 구현은 미확정.
>
> **역할:** N-01의 검색 후보를 원문과 연결하여 후속 노드가 이용할 `NodeResult[EvidenceBundle]`을 구성한다.

관련 문서: [Small Node 목록](README.md) · [공통 반환 계약](common-result-contract.md) · [N-01 검색 후보](N-01.md) · [문서 처리 파이프라인](../document-pipeline.md)

## 1. 단일 책임

N-01에서 전달된 검색 후보의 `chunk_id`, 문서 ID·버전 등의 참조로 원문 블록을 조회하고, 필요한 주변 문맥과 기존 출처 위치를 연결해 `EvidenceBundle`로 반환한다. 새로운 검색·답변 생성·사실 검증은 수행하지 않는다.

## 2. 최소 입출력 (개념 수준)

| 구분 | 현재 등록된 내용 |
|---|---|
| 입력 | `RetrievalCandidates`의 후보 참조(`chunk_id` 등), 문서 ID·버전, 문맥 확장 설정 |
| 처리 | 후보·문서 버전 확인 → 청크와 원문 매핑 조회 → 주변 문맥 확장 → 출처 참조 보존 |
| 출력 | `NodeResult[EvidenceBundle]` (`status`, `data`, `diagnostics`, `outcome`) |

## 3. 문맥 확장 방식 (MVP 확정)

**MVP에서는 고정 길이 문맥 확장을 먼저 구현한다.** 검색된 청크가 가리키는 원문을 기준으로 앞뒤의 일정 범위만 추가로 조회하며, 구조적 관계를 추론하는 별도 확장 로직은 넣지 않는다.

- 확장 범위는 **설정값**으로 두고, 실제 길이와 단위(예: 문자·토큰)는 구현·실험 과정에서 결정한다.
- **동일한 허용 문서·버전·범위 안에서만** 확장한다. 원문 또는 권한 경계를 넘어가지 않으며, 끝에 도달하면 해당 지점에서 잘라낸다.
- 검색용 가공 텍스트가 아닌 **원문 저장 데이터**를 기준으로 확장하고, 가능한 `document_id`, `document_version`, `chunk_id`, `block_id`, `source_locator` 등 **기존 출처 참조**를 보존한다.
- 표 제목·행/열 헤더·각주·상위 제목을 **구조적으로 찾아 붙이는 기능은 MVP에 포함하지 않는다**. 단, 원문에 이미 존재하는 텍스트나 위치 메타데이터를 읽는 것은 허용한다. 누락된 구조를 임의로 추측하지 않는다.
- N-01이 후보를 찾지 못한 경우와 일부 원문 조회가 실패한 경우의 상세 상태 처리 기준은 N-02 계약을 설계할 때 따로 정한다.

## 4. 추후 개선: 문서 구조 기반 확장

파싱·청킹 단계에 문단 계층, 표·헤더·각주 등 **신뢰할 수 있는 구조 참조**가 준비되면 고정 길이 확장 대신 구조 기반으로 관련 문맥을 선택하는 방식을 검토한다.

**교체 가능성을 위해 확장 로직과 외부 반환 계약을 구분한다.** 확장 방식이 바뀌더라도 N-02의 역할 및 `NodeResult[EvidenceBundle]` 공통 외피는 유지하고, 필요한 경우 `EvidenceBundle` 세부 필드·설정만 별도 협의한다. MVP에서 구조 기반 확장까지 구현하거나 두 방법을 동시에 운영할 필요는 없다.

## 5. 후속 검토

- 고정 길이 설정의 구체 단위·기본값·출력 크기 상한
- `EvidenceBundle` 상세 데이터 필드 및 입력 참조 타입
- 원문 누락·권한/버전 불일치·일부 조회 실패 처리와 테스트 기준
- 구현 후 문맥 누락 사례를 분석하여 구조 기반 확장의 도입 필요성 평가

**경계:** 업무별 노드 조합·Big Node 조건부 엣지는 이 문서에 두지 않는다. MVP에서 내부 보조 함수를 Tiny Node 계층으로 분할하지 않는다.
