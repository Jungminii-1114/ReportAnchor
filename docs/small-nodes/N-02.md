# N-02 · get_source_context — 원문 근거 조회

> **상태:** **MVP 문맥 확장 방식·입출력 개념 계약·예외 처리 원칙 확정(2026-11-03)**. 고정 길이 확장을 사용하며, 문서 구조 기반 확장은 추후 개선 후보. 실제 Python 타입, 고정 문맥 확장 길이·출력 상한 및 구현은 미정. **원문 오프셋 기준은 MVP 확정.**
>
> **역할:** N-01의 검색 후보를 원문과 연결하여 후속 노드가 사용할 `NodeResult[EvidenceBundle]`을 구성한다.

관련 문서: [Small Node 목록](README.md) · [공통 반환 계약](common-result-contract.md) · [N-01 검색 후보](N-01.md) · [문서 처리 파이프라인](../document-pipeline.md) · [아티팩트 저장](../artifact-capture.md)

## 1. 단일 책임과 경계

N-01의 후보 `chunk_id`와 문서 ID·버전으로 원문 블록을 조회하고, **기존 출처 위치를 유지하며 원문 앞뒤의 고정 길이 문맥을 확장**해 `EvidenceBundle`로 반환한다.

- **담당:** 후보 참조·권한·버전 검증, 청크와 원문 위치 매핑, 원문 조회·고정 길이 문맥 확장, 출처 보존, 조회 실패 진단.
- **비담당:** 새로운 Dense/BM25 검색·재순위화(N-01), 문서 파싱·청킹·색인 생성(사전 처리), 구조 기반 표/각주 연결(MVP 범위 밖), 답변 생성·근거가 주장에 충분한지 최종 판정(N-03 및 업무 노드).
- 구현 시에도 **LangGraph Small Node는 N-02 하나**로 두고, 내부 조회·확장 보조 기능은 일반 함수/모듈로 구성한다. Tiny Node 분해는 MVP 이후 별도 검토한다.

## 2. 입력 계약 (개념 필드·의미 확정)

| 입력 필드 | 구분 | 의미 및 요구사항 |
|---|---|---|
| `retrieval_candidates` | **필수** | N-01의 **`NodeResult.data: RetrievalCandidates`**. 각 후보의 `chunk_id`, `document_id`, `document_version`, `rank` 등을 사용. 검색 점수나 N-01 진단 전체를 복제할 필요 없음 |
| `document_scope` | **필수** | 원문 조회·앞뒤 확장에 허용된 문서·버전·접근 범위. 후보마다 재검증하며 확장 중에도 범위를 넘지 않음 |
| `context_profile` | **필수 설정 참조** | 고정 길이 확장량·방식·출력 상한의 설정 ID/버전. 구체 길이·단위는 구현 시 결정 |

**원문 조회의 전제:** `ParsedDocument`, `ChunkSet`과 청크-원문 매핑이 이미 생성·저장되어 있어야 한다. N-02가 입력으로 원문 파일 전체를 받거나 청킹을 다시 수행하지는 않는다.

**N-01과의 연결:** `retrieval_candidates`는 N-01의 결과 데이터이고, N-01의 `status/diagnostics/outcome`은 상위 실행 상태에서 별도로 보존한다. N-01 `status=error`로 `data=null`이거나 후보 목록이 0개라면 **상위 호출자는 N-02 호출을 생략**하는 것을 기본 원칙으로 한다. 특히 N-01의 `partial + candidates=[]`을 `no_candidates`로 다시 해석하지 않는다. 후보가 있다면 N-01이 `partial`이었어도 N-02는 자체 조회 결과로 상태를 결정한다.

## 3. 청크와 원문을 잇는 필수 위치 정보 (확정)

**청킹 단계의 `ChunkSet`은 `chunk_id`마다 `source_spans[]`를 보존한다.** N-02는 청크의 검색용 가공 텍스트를 다시 원문에서 찾아 맞추지 않고, 이 매핑으로 실제 `ExtractedBlock.raw_content`의 범위를 조회한다.

~~~json
{
  "chunk_id": "chunk_042",
  "document_id": "doc_01",
  "document_version": "v1",
  "source_spans": [
    {
      "block_id": "block_012",
      "start_offset": 120,
      "end_offset": 240
    }
  ]
}
~~~

### 원문 위치 범위 규칙 — MVP 확정

| 규칙 | 확정 기준 |
|---|---|
| **기준 텍스트** | 청킹 당시 저장한 `ExtractedBlock.raw_content`. PDF/HWP 바이너리, 정규화·토큰화한 검색 표현이 아님 |
| **오프셋 단위** | Python 문자열 인덱스와 같은 **유니코드 코드 포인트** 단위. UTF-8 바이트나 화면 표시 글자(자소 묶음) 단위가 아님 |
| **인덱스 시작** | 각 원문 블록의 첫 코드 포인트를 **0**으로 셈 |
| **시작·끝 규칙** | `[start_offset, end_offset)` : 시작 포함·끝 제외. 해당 범위는 `raw_content[start_offset:end_offset]`와 일치해야 함 |
| **복수 원문 블록** | `source_spans[]`에 `block_id`별 범위를 **원문 순서대로** 기록. 청크 하나가 여러 블록을 가리킬 수 있음 |
| **원문 버전 일치** | N-02가 조회하는 `ParsedDocument`는 **청킹에 사용한 바로 그 파싱 결과 스냅샷**과 일치해야 함. 문서 버전뿐 아니라 원문 블록 내용·파서/설정 버전·아티팩트 참조(또는 해시)를 검증하고 불일치하면 재매핑을 추측하지 않고 `error` 처리 |

검증 조건: `0 <= start_offset <= end_offset <= len(raw_content)`를 만족해야 하며, 실제 텍스트 범위와 매핑이 일치해야 한다. 예를 들어 `raw_content="가나다라마"`에 `start_offset=1`, `end_offset=4`라면 추출 텍스트는 `"나다라"`다.

- 원문 블록의 `raw_content`가 텍스트가 아닌 요소라면 임의의 텍스트 오프셋을 만들지 않는다. 이미지/도형/구조화 표의 비텍스트 영역은 기존 `source_locator` 등 지원 가능한 참조로 구분하고, 텍스트 범위를 지원하지 못하면 원문 조회 가능 여부와 한계를 진단한다.
- `source_locator`(PDF 페이지·좌표·문서 요소 인덱스 등)는 **원문 블록 내부의 문자열 오프셋과 별개**의 출처 위치 정보이며, 가능한 범위에서 함께 보존한다.
- 오프셋 계산 기준은 **MVP에서 고정**했지만, 문맥을 앞뒤로 몇 글자/토큰 확장할지 정하는 **확장 길이 설정과 단위는 별도 미정**이다.

## 4. 문맥 확장 방식 (MVP 확정)

**MVP는 고정 길이 문맥 확장**을 구현한다. `source_spans[]`를 기준으로 원문 시작·끝 위치를 식별하고, 같은 허용 범위의 앞뒤 원문 텍스트를 `context_profile`에 설정된 길이만큼 조회한다.

- 원문 앞뒤 범위가 문서의 시작·끝이나 접근 가능 범위에 닿으면 그 위치에서 확장을 끝낸다. 이것만으로 실행 실패가 되는 것은 아니다.
- 표 제목·행/열 헤더·각주·상위 제목을 **구조적으로 추적해 추가하는 기능은 MVP 범위 밖**이다. 이미 파싱된 블록 내용이나 위치 참조는 그대로 활용한다.
- **근거 단위 (2026-11-05 결정):** 후보 1개당 `evidence_items[]` 항목 1개를 만든다. 문맥이 겹쳐도 병합하지 않고, 같은 `chunk_id`의 중복만 제거한다. 후속 노드의 `evidence_refs[]` 값은 `chunk_id`다.
- 추후 파싱·청킹의 구조 참조가 신뢰할 수 있게 마련되면, **동일한 N-02 계약을 유지하며 문서 구조 기반 확장으로 교체**할 수 있도록 확장 로직을 분리한다. 두 방식을 MVP에서 동시에 구현하지 않는다.

## 5. 출력 계약: `NodeResult[EvidenceBundle]` (개념 필드·의미 확정)

공통 반환 필드 네 가지 `status`, `data`, `diagnostics`, `outcome`은 [공통 계약](common-result-contract.md)을 따른다. 아래 표는 `data: EvidenceBundle`의 내부 구조다.

| `data` 내부 필드 | 역할 |
|---|---|
| `request_ref` | N-01에서 넘어온 요청·질의 추적 참조 |
| `evidence_items[]` | 원문 조회와 문맥 확장이 완료된 근거 항목 목록 |
| `context_profile_ref` | 사용한 확장 설정 ID/버전 |

각 `evidence_items[]` 원소는 다음 필드를 갖는다.

| 근거 항목 필드 | 역할 |
|---|---|
| `chunk_id` | N-01 후보와 연결되는 검색 청크 ID |
| `document_id` · `document_version` | 원문 조회에 사용한 문서·버전 |
| `retrieval_rank` | N-01에서 이미 정해진 후보 순위 보존; N-02가 새 순위를 매기지 않음 |
| `context_text` | 검색 청크가 가리키는 **실제 원문과 앞뒤 확장 문맥**을 담은 텍스트 |
| `source_refs[]` | 근거 청크가 가리키는 `block_id`, 원문 범위(`source_spans`)와 가능한 `source_locator`(페이지·좌표 등) |
| `context_truncated` | 원문 끝·접근 경계·설정된 출력 길이 등으로 요청 문맥이 잘렸는지 표시 |

**원문 범위의 기준점:** `source_refs[]`는 **검색된 원문 부분의 출처**를 유지한다. `context_text`는 더 넓은 주변 텍스트이므로 전체 문맥을 하나의 인용 위치로 간주하지 않는다. 세부적인 원문 부분과 확장 문맥의 별도 범위 표현은 실제 스키마에서 정한다. 구조를 추측해 표·각주 정보를 사실처럼 채우지 않는다.

**가상 반환 예시** (필드 구조 설명용, 실제 실행 결과 아님):

~~~json
{
  "status": "success",
  "data": {
    "request_ref": "req_001",
    "context_profile_ref": "fixed-window-v1",
    "evidence_items": [
      {
        "chunk_id": "chunk_042",
        "document_id": "doc_01",
        "document_version": "v1",
        "retrieval_rank": 1,
        "context_text": "2025년 영업이익은 전년 대비 15% 증가하였다.",
        "source_refs": [
          {
            "block_id": "block_012",
            "start_offset": 120,
            "end_offset": 240,
            "source_locator": {
              "page": 12
            }
          }
        ],
        "context_truncated": false
      }
    ]
  },
  "diagnostics": {
    "validate_source_refs": {"status": "success"},
    "resolve_source_spans": {"status": "success"},
    "expand_context": {"status": "success"}
  },
  "outcome": null
}
~~~

문서 형식이 페이지를 제공하지 않으면 `source_locator.page`를 임의로 만들지 않는다. 실제 `data` 타입·직렬화 세부 제약은 구현 단계에서 결정한다.

## 6. 예외 상황 및 반환 상태 (확정)

| 상황 | 처리 원칙 |
|---|---|
| 모든 후보의 원문과 요청된 문맥 조회 성공 | `status=success`, 정상 `EvidenceBundle` 반환 |
| 일부 후보만 **항목 조회 불가** (블록 없음, 비텍스트 블록, 일시적 읽기 실패) | `status=partial`, 유효한 `evidence_items[]` 보존. 실패 후보는 `diagnostics`의 `failed_items[]`에 `chunk_id`로 기록 |
| 모든 후보의 원문 조회 실패 | `status=error`, 원칙적으로 `data=null`. 실패 후보는 `failed_items[]`에 기록 |
| **무결성 위반** (허용 범위 밖 문서, 권한 거부, 문서 버전 불일치, 파싱 스냅샷 불일치, 오프셋이 원문과 안 맞음) | **1건이어도 전체** `status=error`, `data=null`. 잘못된 참조를 임의로 다른 문서/버전으로 대체하지 않음 |
| 원문 또는 허용 범위 끝에 도달해 확장 종료 | 정상 조회 자체는 `success`. 잘림 여부는 `context_truncated`에 기록 |
| N-01의 후보 0개 | **상위 워크플로에서 N-02 호출 생략** (N-01의 상태·진단 정보는 그대로 보존) |
| 전체 출력 상한 초과 | 낮은 순위 후보부터 제외. 실패가 아니므로 `status`는 유지하고, 제외한 `chunk_id`를 진단에 기록 |
| 빈 후보 목록이 직접 입력됨 | `status=success`, 원문 조회 없이 빈 `evidence_items[]` 반환 |
| `retrieval_candidates`가 `null` | `status=error`, `data=null`. 앞 단계 실패를 빈 목록으로 바꾸어 처리하지 않음 |

- **`partial`과 `error`의 경계 (2026-11-05 결정):** 무결성 위반은 색인과 자료가 어긋났다는 신호이므로 나머지 후보도 믿을 수 없어 전체를 `error`로 처리한다. 항목 조회 불가는 해당 항목만의 문제이므로 나머지 근거로 `partial`을 반환한다.
- N-01과 N-02는 **각각 자신의 실행 상태**를 반환한다. N-01 `partial`이 N-02 `partial`을 자동으로 의미하지 않는다.
- 원문 참조가 부정확하거나 문서 버전이 섞인 데이터를 `partial`로 조용히 통과시키지 않는다.
- 표·헤더·각주 구조가 자동으로 따라오지 않는 것은 **MVP 고정 길이 확장의 알려진 한계**이지, 구조 보강 단계를 수행하지 않았다는 이유만으로 `partial`이 되는 것은 아니다.
- N-02는 문맥·출처 참조의 유효성을 확인하지만, **원문 내용의 사실성이나 주장에 대한 근거 충분성은 판단하지 않는다**.

## 7. 후속 구현·검증 항목

- 고정 길이 확장의 단위, 앞뒤 기본값, 블록 경계에서의 텍스트 연결 규칙, 최대 출력 길이
- 확정된 코드 포인트·`[start, end)` 기준의 실제 파서/청킹 연동 테스트, 파서 버전·원문 해시가 바뀌었을 때 불일치 검출
- `context_text` 내 원래 검색 부분과 확장된 부분의 경계 표기
- 일부 조회 실패를 재현하는 테스트와 출처 범위·권한·버전 검증
- H-02 아티팩트 저장에서 원문 내용을 불필요하게 복제하거나 민감한 원문을 노출하지 않도록 저장 정책 적용
- 구조 기반 확장 필요성은 MVP 관측 결과를 보고 후속 결정

**결정 경계:** N-02의 책임, 입출력 개념 필드, 고정 길이 확장, `source_spans[]` 보존, **원문 위치 기준 6개 규칙** 및 예외 상태는 MVP 확정. 고정 확장 길이·출력량·세부 Python 타입·코드 구현·테스트는 미완료.
